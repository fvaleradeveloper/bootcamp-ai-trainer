📦 Módulo 1 — Asincronía JS/Node.js

Teoría esencial

JavaScript es single-threaded con un event loop. Las promesas se resuelven en la microtask queue (prioridad alta), mientras que setTimeout y I/O van a la macrotask queue.

Los 4 combinadores de promesas

MétodoResuelve cuandoRechaza cuando
Promise.allTodas resuelvenLa primera rechaza
Promise.allSettledTodas terminan (resuelven o rechazan)Nunca
Promise.raceLa primera que termina (resuelve o rechaza)La primera que termina
Promise.anyLa primera que resuelveTodas rechazan

Radar de 6 patrones bug-prone en async JS

forEach + async — no espera las promesas
Promise.all sin catch — un rechazo hunde todo
Sin finally en recursos — conexiones/pools se agotan
Race conditions — read-modify-write sin lock
Concurrencia sin límite — 10000 requests simultáneos
await en loop secuencial — cuando podría ser paralelo

📚 Teoría M1 — Event loop, microtareas y los 4 combinadores (léeme antes de los ejercicios)

JS ejecuta tu código en un solo hilo. Lo async no corre en paralelo: se encola. Regla de oro: await cede el hilo; todo lo que esté después del await corre después, y mientras tanto el event loop atiende otras microtareas. Por eso el orden "leer → await → escribir" nunca es atómico.

1. Microtarea vs macrotarea (el orden que te preguntan en el examen)
  • Microtareas (prioridad alta, se vacían por completo antes de pintar): Promise.then/catch/finally, queueMicrotask, await resuelto.
  • Macrotareas (una por vuelta del loop): setTimeout/setInterval, I/O, eventos UI.
  • Trampa clásica: Promise.resolve().then(f) corre antes que setTimeout(f, 0). Si un reviewer dice "el timeout corre primero", está mal.
2. Los 4 combinadores — cuándo usar cada uno
  • Promise.all: todo-o-nada. Un rechazo cancela el resultado (las demás siguen corriendo pero su valor se pierde). Úsalo solo si el lote es homogéneo y quieres fallar rápido.
  • Promise.allSettled: para lotes heterogéneos (50 endpoints). Nunca rechaza; inspecciona {status, value, reason} por item.
  • Promise.race: la primera que termina (resuelva o rechace). Patrón timeout: race([fetch(url), timeout(5000)]).
  • Promise.any: la primera que resuelve. Solo rechaza (AggregateError) si todas fallan. Ideal para mirrors/fallbacks.
3. Los 3 bugs que más suspenden
  • forEach + async: forEach ignora el return del callback → las promesas quedan huérfanas. Paralelo: await Promise.all(arr.map(f)). Secuencial: for...of.
  • Recurso sin finally: si hay throw entre acquire() y release(), el pool se agota. Patrón: try { usar } finally { liberar }.
  • fetch sin res.ok: fetch solo rechaza por fallo de red. Un 404/500 llega como response "exitosa". Siempre: if (!res.ok) throw ....
4. Cómo responder en el examen (aplica a 1.1–1.4)

Qué falla (una frase) → por qué (mecanismo del event loop/promesa) → cuándo (qué input o timing lo dispara) → corrección mínima → verificación (assert con el caso que antes fallaba).

  • Explicas el orden microtarea vs macrotarea sin dudar.
  • Eliges el combinador correcto (all / allSettled / race / any) según el caso.
  • Detectas forEach+async, falta de finally y fetch sin res.ok a simple vista.

Ejemplo resuelto 0.0 — forEach async devuelve []

// BUG: forEach no espera promesas
async function obtenerNombres(ids) {
  const nombres = [];
  ids.forEach(async (id) => {
    const res = await fetch(`/api/users/${id}`);
    const data = await res.json();
    nombres.push(data.name);
  });
  return nombres; // siempre devuelve []
}

Qué falla: forEach ignora el valor retornado del callback. Las funciones async dentro devuelven promesas que nadie espera.

Corrección: Usar for...of (secuencial) o Promise.all(arr.map(...)) (paralelo).

Ejercicio 1.1 — forEach async en notificaciones

Asincronía JS Facil✅ Completado

Este código debe enviar notificaciones a todos los usuarios y devolver el total enviados. Pero total siempre es 0.

async function enviarNotificaciones(usuarios) {
  let total = 0;
  usuarios.forEach(async (user) => {
    await enviarEmail(user.email, "Tienes una alerta");
    total++;
  });
  console.log(`Enviadas: ${total}`);
  return total;
}

Pista: ¿Qué devuelve forEach? ¿Espera acaso las promesas que retorna el callback async? Piensa en el orden de ejecución: la línea del console.log se ejecuta antes de que cualquier await dentro del callback se resuelva.

Pista 2 (guiada): Mira el .forEach: su callback devuelve una promesa que nadie guarda. Preguntate: despues del bucle, quien hace await a esos envios?

1. ¿Qué falla? forEach no espera las promesas del callback async, por lo que total se retorna antes de que se ejecute cualquier incremento.

2. ¿Por qué falla? Array.prototype.forEach ignora completamente el valor de retorno del callback. Cuando el callback es async, devuelve una Promise que se descarta. El loop termina sincrónicamente y la función continúa.

3. ¿Cuándo se manifiesta? Siempre. El console.log imprime 0 en el 100% de las ejecuciones.

4. Corrección:

async function enviarNotificaciones(usuarios) {
  const promesas = usuarios.map(async (user) => {
    await enviarEmail(user.email, "Tiene una alerta");
  });
  await Promise.all(promesas);
  const total = usuarios.length;
  console.log(`Enviadas: ${total}`);
  return total;
}

5. Verificación:

// Mock
let enviados = 0;
async function enviarEmail() { enviados++; }
const r = await enviarNotificaciones([{email:"a@b.com"},{email:"c@d.com"}]);
console.assert(r === 2);
console.assert(enviados === 2);

Ejercicio 1.2 — Promise.all que colapsa con un 404

Promesas + HTTP JS Media✅ Completado

Debe obtener datos de 50 endpoints. Si uno falla, no se obtiene ninguno. Además, no verifica res.ok y lanza 50 requests simultáneos.

async function obtenerTodo(urls) {
  const results = await Promise.all(
    urls.map(url => fetch(url).then(r => r.json()))
  );
  return results;
}

Pista: Tres problemas: (1) ¿Qué pasa si un fetch devuelve 404? fetch no rechaza por status HTTP. (2) ¿Qué hace Promise.all cuando una promesa rechaza? (3) ¿Qué pasa con 1000 URLs simultáneas?

Pista 2 (guiada): Mira el .map con fetch: falta res.ok y un solo rechazo hunde Promise.all. Preguntate: que devuelve el lote si el item 7 es un 404?

1. ¿Qué falla? Tres bugs: no verifica res.ok (un 404 se trata como éxito), Promise.all falla completo si un request rechaza, y no hay límite de concurrencia.

2. ¿Por qué falla? fetch() solo rechaza por errores de red, no por status 4xx/5xx. Un 404 devuelve una response válida cuyo .json() puede fallar con un error de parsing, rechazando la promesa y hundiendo todo el Promise.all.

3. ¿Cuándo se manifiesta? Cuando un endpoint devuelve 404/500, o cuando hay muchas URLs y se satura el pool de conexiones del navegador/Node.

4. Corrección:

async function obtenerTodo(urls, concurrencia = 10) {
  const resultados = await Promise.allSettled(
    urls.map(async (url) => {
      const res = await fetch(url);
      if (!res.ok) throw new Error(`HTTP ${res.status} en ${url}`);
      return res.json();
    })
  );
  return resultados.filter(r => r.status === "fulfilled").map(r => r.value);
}
// Para concurrencia limitada, usar un pool o p-limit

5. Verificación:

const urls = ["/ok1", "/ok2", "/404", "/ok3"];
const r = await obtenerTodo(urls);
console.assert(r.length === 3); // los 3 OK, el 404 se excluye

Ejercicio 1.3 — Conexión DB sin finally

Recursos JS Media✅ Completado

Tras horas de tráfico, la aplicación deja de responder. El pool de conexiones se agota.

async function getUser(id) {
  const client = await pool.connect();
  const result = await client.query("SELECT * FROM users WHERE id = $1", [id]);
  return result.rows[0];
}

Pista: ¿Qué pasa si client.query() lanza una excepción? ¿Se libera la conexión? ¿Dónde debería estar client.release() para garantizarse siempre?

Pista 2 (guiada): Sigue el camino con throw entre getConnection() y release(). Preguntate: en que camino el release() nunca corre?

1. ¿Qué falla? La conexión nunca se libera al pool. Si la query falla, client.release() ni siquiera existe en el código, y aunque existiera sin finally, no se ejecutaría en caso de error.

2. ¿Por qué falla? Cada pool.connect() toma una conexión del pool. Sin client.release() en un bloque finally, la conexión se queda ocupada para siempre. Tras N errores, el pool (típicamente 10-20 conexiones) se agota.

3. ¿Cuándo se manifiesta? Tras el primer error de query (constraint violation, timeout, etc.). Progresivamente todas las requests se bloquean esperando una conexión disponible.

4. Corrección:

async function getUser(id) {
  const client = await pool.connect();
  try {
    const result = await client.query("SELECT * FROM users WHERE id = $1", [id]);
    return result.rows[0];
  } finally {
    client.release();
  }
}

5. Verificación:

// Simular error y verificar que el pool no se agota
for (let i = 0; i < 50; i++) {
  try { await getUser("invalid-id"); } catch(e) {}
}
// El pool debería seguir teniendo conexiones disponibles
console.assert(pool.totalCount === pool.idleCount);

Ejercicio 1.4 — Race condition en contador

Concurrencia JS Dificil✅ Completado

10 llamadas simultáneas a incrementar deberían dar 10, pero a veces da 1.

let contador = 0;

async function incrementar() {
  const actual = contador;
  await simularLatencia(); // 10-100ms
  contador = actual + 1;
}

// Uso:
Promise.all(Array(10).fill(0).map(() => incrementar()));
console.log(contador); // esperado: 10, obtenido: 1

Pista: Todas las llamadas leen contador antes del await. ¿Qué valor leen las 10? Después del await, ¿a cuánto escriben? Es el clásico patrón read-modify-write sin atomicidad.

Pista 2 (guiada): Fijate que las 10 llamadas leen contador ANTES del await. Preguntate: que valor leen las 10 si ninguna escribio todavia?

1. ¿Qué falla? Las 10 llamadas leen contador = 0 antes del await, y después del await todas escriben 0 + 1 = 1. Es una race condition clásica.

2. ¿Por qué falla? El patrón read-modify-write no es atómico. Entre la lectura (const actual = contador) y la escritura (contador = actual + 1), el event loop ejecuta otras microtasks. Las 10 funciones leen el mismo valor antes de que cualquiera escriba.

3. ¿Cuándo se manifiesta? Siempre que haya concurrencia real (múltiples llamadas antes de que la primera termine de escribir). En Node.js con operaciones async (DB, red, timers).

4. Corrección:

// Opción A: Mutex/lock simple
let contador = 0;
let lock = Promise.resolve();

async function incrementar() {
  const prev = lock;
  let release;
  lock = new Promise(r => release = r);
  await prev;
  try {
    contador++;
  } finally {
    release();
  }
}

// Opción B (mejor): usar un contador atómico sin await en medio
let contador = 0;
function incrementar() {
  contador++; // síncrono, no hay race condition
}

5. Verificación:

await Promise.all(Array(10).fill(0).map(() => incrementar()));
console.assert(contador === 10);

📚 Teoría M2 — Excepciones, mutabilidad y truthiness (léeme antes de los ejercicios)

En Python los 3 suspensos clásicos son: tragar errores con except:, compartir estado con defaults mutables, y confundir "falsy" con "ausente". Los tres se detectan con la misma pregunta: ¿qué valores concretos pueden llegar aquí?

1. Excepciones: captura lo específico, nunca lo desnudo
  • except: captura hasta KeyboardInterrupt y SystemExit, y esconde typos (NameError) que deberían crashear en desarrollo.
  • Patrón examen: except (ValueError, TypeError): + log del input + valor por defecto documentado. Y si no sabes recuperarte, no captures.
  • try/except/else/finally: el else corre solo si no hubo excepción (ideal para separar "parseo" de "uso").
2. Defaults mutables: el objeto se crea UNA vez
  • def f(cache={}): ese dict se crea al definir la función y se comparte entre todas las llamadas. Fuga de datos entre usuarios.
  • Patrón: def f(cache=None): cache = {} if cache is None else cache. Lo mismo para [] y set().
  • Variante en clases: atributo de clase mutable vs atributo de instancia. Si lo mutas en instancia, contamina a todas.
3. Truthiness: 0 es un valor, no una ausencia
  • Falsy: None, False, 0, 0.0, "", [], {}, set(). Todo lo demás es truthy.
  • if porcentaje: trata 0 como "no proporcionado". Para opcionales usa centinela: def f(x=None): if x is not None:.
  • En paginación offset=0 es válido; en descuentos 0% es válido. Si tu check los descarta, el bug es conceptual aunque el número "coincida".
  • Distingues except: de except (ValueError, TypeError): y sabes qué traga cada uno.
  • Ves un default mutable y lo corriges con centinela None sin pensar.
  • Nunca usas if x: para detectar "parámetro omitido" con valores 0/"" válidos.

class Carrito:

c1 = Carrito()
c1.items.append("manzana")

c2.items.append("pera")

Ejercicio 2.1 — Parser de precios con except desnudo

Excepciones PY Facil✅ Completado

Este parser convierte strings a precios. Cuando recibe None, devuelve 0.0 silenciosamente. El equipo de datos no sabe que hay nulls en la base.

def parse_precio(texto):
    try:
        limpio = texto.strip().replace("$", "").replace(",", "")
        return float(limpio)
    except:
        return 0.0

Pista: ¿Qué captura un except: sin tipo? Si texto es None, ¿qué excepción lanza None.strip()? ¿Y si el usuario presiona Ctrl+C durante el procesamiento? ¿Se captura también?

Pista 2 (guiada): Cuenta que errores lanza float() con None, texto o Infinity. Preguntate: cuales deberian ser 0 y cuales deberian crashear?

1. ¿Qué falla? El except: desnudo captura TODAS las excepciones, incluyendo TypeError (cuando texto es None), KeyboardInterrupt y SystemExit. Devuelve 0.0 sin distinguir entre "formato inválido" y "error grave".

2. ¿Por qué falla? En Python, except: sin tipo equivale a except BaseException:. Captura incluso KeyboardInterrupt y SystemExit, haciendo el proceso imposible de matar limpiamente. Además, enmascara bugs de programación (como pasar None) que deberían fallar rápido.

3. ¿Cuándo se manifiesta? Cuando llega un None de la BD, cuando hay un typo en el código dentro del try, o cuando el usuario intenta cancelar el proceso.

4. Corrección:

def parse_precio(texto):
    if texto is None:
        raise ValueError("Precio no puede ser None")
    try:
        limpio = texto.strip().replace("$", "").replace(",", "")
        return float(limpio)
    except (ValueError, AttributeError) as e:
        raise ValueError(f"Precio inválido: {texto!r}") from e

5. Verificación:

assert parse_precio("$1,234.56") == 1234.56
try:
    parse_precio(None)
    assert False, "Debería lanzar"
except ValueError:
    pass
try:
    parse_precio("abc")
    assert False
except ValueError:
    pass

Ejercicio 2.2 — Caché compartido entre usuarios

Mutabilidad PY Media✅ Completado

Esta función cachea resultados de consultas. Pero los usuarios empiezan a ver datos de otros usuarios.

def obtener_datos(usuario_id, cache={}):
    if usuario_id not in cache:
        cache[usuario_id] = db.query("SELECT * FROM datos WHERE user_id = %s", usuario_id)
    return cache[usuario_id]

Pista: ¿Cuántas veces se evalúa el default cache={}? ¿Es una lista nueva por llamada o se evalúa una sola vez? ¿Qué implica eso para múltiples llamadas a la función?

Pista 2 (guiada): Busca donde se crea el {} del default y cuantas veces se evalua. Preguntate: es un dict nuevo por llamada o el mismo siempre?

1. ¿Qué falla? El diccionario cache={} como argumento por defecto se crea UNA SOLA VEZ cuando Python define la función. Todas las llamadas comparten el mismo diccionario.

2. ¿Por qué falla? Los argumentos por defecto en Python se evalúan una sola vez, en tiempo de definición de la función. El objeto mutable (dict) persiste entre llamadas. Esto es un patrón bien conocido pero peligroso.

3. ¿Cuándo se manifiesta? Desde la segunda llamada. Si el usuario A se cachea primero, y luego el usuario B tiene el mismo ID en otro contexto, o si el cache crece sin límite causando memory leak.

4. Corrección:

def obtener_datos(usuario_id, cache=None):
    if cache is None:
        cache = {}
    if usuario_id not in cache:
        cache[usuario_id] = db.query(
            "SELECT * FROM datos WHERE user_id = %s", usuario_id
        )
    return cache[usuario_id]

# O mejor: usar un caché con TTL y límite
from functools import lru_cache
import time

5. Verificación:

c1 = {}
r1 = obtener_datos("user_a", cache=c1)
r2 = obtener_datos("user_b", cache=c1)
assert "user_a" in c1
assert "user_b" in c1
# Sin pasar cache, cada llamada tiene su propio dict
r3 = obtener_datos("user_c")
r4 = obtener_datos("user_d")
# r3 y r4 no comparten estado

Ejercicio 2.3 — if porcentaje: descarta el 0%

Truthiness PY Facil✅ Completado

Esta función aplica un descuento. Cuando el descuento es exactamente 0% (sin descuento), el sistema lo trata como si no se hubiera pasado el parámetro y usa el default del 10%.

def aplicar_descuento(precio, porcentaje=10):
    if porcentaje:
        return precio * (1 - porcentaje / 100)
    return precio

Pista: En Python, bool(0) es False. Si alguien llama aplicar_descuento(100, 0) para indicar "sin descuento", ¿qué rama se ejecuta? ¿Es 0 un valor válido o significa "no proporcionado"?

Pista 2 (guiada): Prueba aplicar_descuento(100, 0) y mira que rama toma el if porcentaje:. Preguntate: 0 significa omitido o cero real?

1. ¿Qué falla? Cuando porcentaje=0, if porcentaje: evalúa a False (porque 0 es falsy), y la función retorna el precio sin descuento en lugar de aplicar el 0% (que matemáticamente es lo mismo, pero el problema es cuando 0 es un valor legítimo que se confunde con "no proporcionado").

2. ¿Por qué falla? Python trata 0, "", [], {}, None y False como falsy. Usar if valor: para verificar "si se proporcionó un parámetro" falla cuando el valor válido es 0.

3. ¿Cuándo se manifiesta? Cuando el caller pasa explícitamente 0 para indicar "sin descuento". El resultado es correcto matemáticamente (precio * 1 = precio), pero el bug es conceptual: el código no distingue entre "no pasado" y "pasado como 0". En otros contextos (ej: offset=0 en paginación) sería un bug funcional.

4. Corrección:

def aplicar_descuento(precio, porcentaje=None):
    if porcentaje is not None:
        if not (0 <= porcentaje <= 100):
            raise ValueError(f"Porcentaje inválido: {porcentaje}")
        return precio * (1 - porcentaje / 100)
    return precio * 0.9  # default 10%

5. Verificación:

assert aplicar_descuento(100, 0) == 100    # 0% = sin descuento
assert aplicar_descuento(100, 50) == 50   # 50% descuento
assert aplicar_descuento(100) == 90      # default 10%
assert aplicar_descuento(100, 100) == 0  # 100% = gratis

📚 Teoría M3 — El checklist de límites que el evaluador sí pasa (léeme antes de los ejercicios)

El 80% de los "edge cases" del examen son 7 casos. Memoriza la lista y pásala mentalmente a cada función: vacío, uno, cero, negativo, enorme, duplicado, mixto. Si tu corrección no dice qué hace en cada uno, está incompleta.

1. Off-by-one: el bug más rentable del examen
  • En Python lista[a:b] excluye b. Para N elementos desde i: [i:i+N], nunca [i:i+N-1].
  • En paginación verifica siempre: página 0 empieza en 0, no hay gaps (0-9, 10-19) ni overlaps, y la última página parcial funciona.
  • En bucles: range(n) da 0..n-1. Si quieres 1..n, es range(1, n+1).
2. División por cero y el caso 0→X
  • (actual - anterior) / anterior explota con anterior=0. Decide el contrato: 0→0 = 0%, 0→X = infinito o error documentado. Lo que suspende es no decidir.
  • Lo mismo para promedios (sum([])/len([])), ratios y porcentajes. Guarda vacía primero.
3. Búsqueda binaria: invariante o loop infinito
  • Invariante: el target, si existe, siempre está en [izq, der]. Cada iteración debe achicar el intervalo: izq = medio + 1 o der = medio - 1.
  • izq = medio no achica cuando medio == izq → loop infinito con 2 elementos. Señal de humo: "se cuelga cuando el elemento no está".
  • Verificación mínima: encontrado, no encontrado, vacío, un elemento, duplicados.
  • Pasas el checklist vacío/uno/cero/negativo/enorme/duplicado/mixto a cada función.
  • Corriges slices y rangos sin dudar (exclusivo vs inclusivo).
  • Enuncias el invariante de búsqueda binaria y garantizas progreso del loop.

Ejercicio 3.1 — Crecimiento porcentual con división por cero

Edge cases PY Facil✅ Completado

Calcula el crecimiento porcentual entre dos períodos. Cuando el valor anterior es 0, crashea.

def crecimiento_porcentual(anterior, actual):
    return ((actual - anterior) / anterior) * 100

Pista: ¿Qué pasa cuando anterior = 0? ¿Y cuando ambos son 0? ¿Cuál es el crecimiento porcentual cuando pasas de 0 a 100? ¿Es definible matemáticamente?

Pista 2 (guiada): Prueba anterior=0, actual=100 y anterior=0, actual=0. Preguntate: que contrato (inf, 0 o error) documentarias?

1. ¿Qué falla? ZeroDivisionError cuando anterior = 0. Además, no valida tipos ni rangos.

2. ¿Por qué falla? La fórmula de crecimiento porcentual (actual - anterior) / anterior tiene una singularidad cuando anterior=0. Matemáticamente, pasar de 0 a cualquier valor positivo es un crecimiento infinito/no definido.

3. ¿Cuándo se manifiesta? En el primer período de un producto nuevo (ventas anteriores = 0), o cuando se reinician contadores.

4. Corrección:

def crecimiento_porcentual(anterior, actual):
    if anterior == 0 and actual == 0:
        return 0.0     # sin cambio
    if anterior == 0:
        return float('inf')  # crecimiento infinito
    return ((actual - anterior) / anterior) * 100

5. Verificación:

assert crecimiento_porcentual(100, 150) == 50.0
assert crecimiento_porcentual(0, 0) == 0.0
assert crecimiento_porcentual(0, 100) == float('inf')
assert crecimiento_porcentual(200, 100) == -50.0

Ejercicio 3.2 — Paginación con off-by-one

Off-by-one PY Media✅ Completado

Paginación de resultados. El cálculo del índice final tiene un error que causa duplicación o pérdida de elementos entre páginas.

def paginar(items, pagina, por_pagina=10):
    inicio = pagina * por_pagina
    fin = inicio + por_pagina - 1
    return items[inicio:fin]

Pista: En Python, los slices lista[a:b] son exclusivos en el límite superior. Si quieres 10 elementos empezando en 0, ¿cuál es el slice correcto: [0:9] o [0:10]? ¿Cuántos elementos devuelve [0:9]?

Pista 2 (guiada): Cuenta los elementos de items[0:9] vs items[0:10]. Preguntate: el limite superior del slice es inclusivo o exclusivo?

1. ¿Qué falla? El -1 en fin = inicio + por_pagina - 1 causa que cada página devuelva un elemento menos. Con por_pagina=10, solo devuelve 9.

2. ¿Por qué falla? El autor confunde la semántica de slices de Python con índices inclusivos. En Python, lista[a:b] va desde el índice a hasta b-1 (b exclusivo). Para obtener 10 elementos desde inicio, el slice es [inicio:inicio+10], no [inicio:inicio+9].

3. ¿Cuándo se manifiesta? Siempre. Cada página pierde el último elemento. La página 0 devuelve items[0:9] (9 elementos en vez de 10).

4. Corrección:

def paginar(items, pagina, por_pagina=10):
    if pagina < 0 or por_pagina < 1:
        raise ValueError("Página y por_pagina deben ser positivos")
    inicio = pagina * por_pagina
    fin = inicio + por_pagina  # sin -1, el slice es exclusivo
    return items[inicio:fin]

5. Verificación:

assert len(paginar(items, 0)) == 10  # [0..9]
assert len(paginar(items, 1)) == 10  # [10..19]
assert len(paginar(items, 2)) == 5   # [20..24]
assert paginar(items, 0)[0] == 0
assert paginar(items, 1)[0] == 10  # sin gap ni overlap

Ejercicio 3.3 — Búsqueda binaria con loop infinito

Algoritmos PY Dificil✅ Completado

Búsqueda binaria que se cuelga indefinidamente cuando el elemento no está en el array.

def busqueda_binaria(arr, target):
    izq, der = 0, len(arr) - 1
    while izq <= der:
        medio = (izq + der) // 2
        if arr[medio] == target:
            return medio
        elif arr[medio] < target:
            izq = medio  # BUG aquí
        else:
            der = medio - 1
    return -1

Pista: Cuando izq=3, der=4, medio=3. Si arr[3] < target, se asigna izq = medio = 3. ¿Cambió algo? ¿Se reduce el rango? ¿Qué pasa en la siguiente iteración?

Pista 2 (guiada): Traza con 2 elementos donde el target no esta y mira si izq cambia. Preguntate: el intervalo se achica en TODAS las ramas?

1. ¿Qué falla? izq = medio en vez de izq = medio + 1. Cuando el rango se reduce a 2 elementos y el target es mayor que el del medio, izq no avanza y el loop se repite infinitamente.

2. ¿Por qué falla? Si izq=3, der=4, entonces medio = (3+4)//2 = 3. Si arr[3] < target, asignamos izq = 3 (sin cambio). La siguiente iteración calcula el mismo medio=3 y entra en loop infinito.

3. ¿Cuándo se manifiesta? Cuando el target no está en el array y la búsqueda converge a un rango de 2 elementos donde el target sería mayor que el elemento central.

4. Corrección:

def busqueda_binaria(arr, target):
    izq, der = 0, len(arr) - 1
    while izq <= der:
        medio = (izq + der) // 2
        if arr[medio] == target:
            return medio
        elif arr[medio] < target:
            izq = medio + 1  # +1 para garantizar progreso
        else:
            der = medio - 1
    return -1

5. Verificación:

arr = [1, 3, 5, 7, 9, 11]
assert busqueda_binaria(arr, 7) == 3
assert busqueda_binaria(arr, 1) == 0
assert busqueda_binaria(arr, 11) == 5
assert busqueda_binaria(arr, 6) == -1   # no existe, no cuelga
assert busqueda_binaria([], 1) == -1   # vacío

Los 5 pecados de seguridad

🚫 Pecados capitales de seguridad
  1. API keys hardcoded — en el código fuente o en logs.
  2. SQL injection — f-strings o concatenación en queries.
  3. Secrets en logs — passwords, tokens, PII en stdout.
  4. Sin validación de input — confiar en lo que envía el cliente.

📚 Teoría M4 — HTTP correcto y seguridad sin perdón (léeme antes de los ejercicios)

En el examen de reviewer la seguridad no es opinable: un SQLi o un secret en logs es severidad crítica aunque "funcione". Y un status mal usado es bug funcional: el cliente automatizado decide por el código, no por el body.

1. Status codes: el contrato que el cliente sí lee
  • 400 input inválido · 401 falta auth · 403 auth ok pero sin permiso · 404 no existe · 409 conflicto (duplicado) · 429 rate limit · 500 fallo nuestro.
  • Nunca devuelvas 200 con {"error": ...}: rompes reintentos, cachés y alertas. Nunca devuelvas 500 con stack trace: regalas internals al atacante.
  • 404 vs 403: si el recurso no existe para ese usuario, 404 (no confirmes que existe). El 403 confirma existencia.
2. SQL injection: parámetros siempre, f-strings nunca
  • f"SELECT ... WHERE id = '{id}'" es inyectable con ' OR '1'='1. La corrección es query parametrizada: WHERE id = $1 + pasar id aparte.
  • Trampa: ORDER BY {col} y LIKE '%{q}%' no se pueden parametrizar como valores. Solución: allowlist de columnas (if col not in {"nombre","precio"}: 400) y escapar %_ en LIKE.
3. Auth: hash, timing y enumeración
  • Passwords: bcrypt/argon2, nunca plaintext ni SHA256 pelado. Comparar hashes con comparación constante (hmac.compare_digest), nunca ==.
  • Login: el error debe ser genérico ("credenciales inválidas") y tardar lo mismo exista o no el usuario. Decir "usuario no existe" = enumeración de usuarios.
  • Secrets (API keys, tokens, PII) jamás en código, logs ni respuestas de error. Van en variables de entorno.
  • Asignas el status correcto (400/401/403/404/409/500) sin dudar.
  • Distingues query parametrizable de identificador dinámico (allowlist).
  • Detectas plaintext, ==, enumeración y secrets en logs al instante.

Endpoint que busca un producto por ID. No devuelve 404 cuando no existe y expone detalles internos en el error.

@app.get("/productos/{id}")
async def get_producto(id: str):
    try:
        producto = db.query(f"SELECT * FROM productos WHERE id = '{id}'")
        return producto
    except Exception as e:
        return {"error": str(e), "query": f"SELECT * FROM productos WHERE id = '{id}'"}

Pista: Cuatro problemas: (1) ¿Qué pasa si el producto no existe? ¿Devuelve 404? (2) ¿Cómo se construye la query? (3) ¿Qué se expone en el error? (4) ¿Qué status code se devuelve cuando hay excepción?

Pista 2 (guiada): Hay 4 hallazgos: status si no existe, f-string en SQL, str(e) en la respuesta y status del error. Busca uno de cada familia.

1. ¿Qué falla? Cuatro bugs: no devuelve 404 si el producto no existe (devuelve null/200), SQL injection por f-string en la query, expone la query SQL completa y el mensaje de error interno al cliente, y no usa HTTPException.

from fastapi import HTTPException

    try:

            "SELECT * FROM productos WHERE id = :id",
            {"id": id}
        )
    except Exception:
        raise HTTPException(status_code=500, detail="Error interno")
    if producto is None:
        raise HTTPException(status_code=404, detail="Producto no encontrado")
    return producto

Seguridad PY Dificil✅ Completado

Endpoint de búsqueda de productos con filtros. Tres vectores de SQL injection.

@app.get("/buscar")
async def buscar(q: str, categoria: str = None, orden: str = "precio"):
    query = f"SELECT * FROM productos WHERE nombre LIKE '%{q}%'"
    if categoria:
        query += f" AND categoria = '{categoria}'"
    query += f" ORDER BY {orden}"

Pista: Tres parámetros del usuario se interpolan directamente en SQL. El parámetro orden es especialmente peligroso porque ORDER BY no acepta parámetros vinculados en la mayoría de ORMs. ¿Cómo whitelistar columnas válidas?

Pista 2 (guiada): Hay 3 inyecciones: LIKE, categoria y ORDER BY. Preguntate: cuales aceptan parametros y cual exige allowlist?

1. ¿Qué falla? Tres vectores de SQL injection: q en LIKE, categoria en WHERE, y orden en ORDER BY. Todos interpolados con f-strings directamente en la query.

2. ¿Por qué falla? Los f-strings no escapan caracteres especiales de SQL. Un atacante puede cerrar comillas e inyectar SQL arbitrario. ORDER BY no se puede parametrizar con $1 en la mayoría de drivers, por lo que requiere whitelist.

        raise HTTPException(400, "Orden inválido")

    params = {"q": f"%{q}%"}
    if categoria:
        query += " AND categoria = :cat"
        params["cat"] = categoria
    query += f" ORDER BY {orden}"  # seguro porque está whitelisted
    return await db.execute(query, params)

📚 Teoría M5 — Frontend que no cobra dos veces ni ejecuta XSS (léeme antes de los ejercicios)

En frontend el examen persigue 3 familias: XSS por innerHTML, doble submit y polling con reentrada. Las tres comparten raíz: confiar en que "el usuario hará click una vez" o "el input es texto inocente". Nunca lo es.

1. XSS: innerHTML es un sink, trátalo como tal
  • el.innerHTML = ...usuario... ejecuta HTML/JS. Vectores del examen: el query q, el título renderizado y el href con javascript:.
  • Corrección por capas: textContent para texto (no interpreta HTML), allowlist de URLs (http/https, bloquea javascript:), y sanitizar/escapar (< > & " ') lo que venga de fuera.
  • En React el equivalente es dangerouslySetInnerHTML: si lo ves sin sanitizar, es hallazgo directo.
2. Doble submit: botón + idempotencia
  • Doble click = dos POST = dos cobros. Defensa en cliente: flag processing + disabled + finally que libera. Defensa real: Idempotency-Key que el servidor guarda (UNIQUE) antes de cobrar.
  • Sin el header, el fix de UI es cosmético: un reintento de red legítimo seguiría cobrando doble. El examen quiere las dos capas.
3. Polling: setInterval miente cuando hay latencia
  • setInterval(poll, 2000) dispara aunque el poll anterior siga vivo → reentrada, respuestas fuera de orden, thundering herd.
  • Patrón: setTimeout recursivo (agenda el siguiente después de terminar) + flag inFlight + dedupe por id + backoff exponencial con jitter ante errores.
  • Enumeras los 3 vectores XSS de un buscador y su fix por capas.
  • Exiges botón bloqueado + Idempotency-Key en cualquier cobro.
  • Sustituyes setInterval por setTimeout recursivo con backoff.

  div.textContent = str;

function esUrlSegura(url) {
  try {
    const u = new URL(url, location.origin);
    return ["http:", "https:"].includes(u.protocol);
  } catch { return false; }

function renderResultados(query, resultados) {

    li.appendChild(a);
    ul.appendChild(li);
  });
  container.appendChild(ul);
  document.getElementById("results").replaceChildren(container);
}

Ejercicio 5.2 — Formulario de pago sin idempotency ni bloqueo

1. ¿Qué falla? No hay bloqueo del botón durante el request, no hay idempotency key, y no se verifica res.ok. Doble click = doble cobro.

2. ¿Por qué falla? Entre el primer click y la respuesta del servidor (puede tardar 2-5 segundos), el botón sigue activo. Cada click dispara un POST independiente. Sin idempotency key, el servidor no puede detectar que son el mismo pago.

3. ¿Cuándo se manifiesta? Con redes lentas, servidores sobrecargados, o usuarios impacientes. Especialmente común en móvil con latencia alta.

4. Corrección:

function uuid() { return crypto.randomUUID(); }

let processing = false;
document.getElementById("pay-btn").addEventListener("click", async () => {
  if (processing) return;
  processing = true;
  const btn = event.target;
  btn.disabled = true;
  btn.textContent = "Procesando...";
  try {
    const res = await fetch("/api/charge", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "Idempotency-Key": uuid()
      },
      body: JSON.stringify({amount: 99.99})
    });
    if (!res.ok) throw new Error(`Error ${res.status}`);
    alert("Pago exitoso!");
  } catch (err) {
    alert("Error en el pago. Intente de nuevo.");
    btn.disabled = false;
    btn.textContent = "Pagar";
    processing = false;
  }
});

Ejercicio 5.3 — Polling con reentrada y sin backoff

Polling UI JS Media✅ Completado

Polling cada 5 segundos para actualizar datos. Cuando el servidor es lento, se acumulan requests.

setInterval(async () => {
  const res = await fetch("/api/status");
  const data = await res.json();
  updateUI(data);
}, 5000);

Pista: Si el fetch tarda 8 segundos pero el intervalo es de 5, ¿qué pasa a los 5 segundos? ¿Se lanza otro fetch mientras el primero sigue pendiente? ¿Qué pasa si el servidor está caído? ¿Hay algún límite o backoff?

Pista 2 (guiada): Dibuja fetch de 8s con intervalo de 5s. Preguntate: cuantos fetch vivos hay a los 10s? Y si el server cae, afloja o martillea?

1. ¿Qué falla? setInterval no espera a que el callback async termine. Si el fetch tarda más de 5s, se acumulan requests concurrentes (reentrada). No hay backoff exponencial cuando el servidor falla, ni deduplicación.

2. ¿Por qué falla? setInterval lanza el callback cada 5s sin importar si el anterior terminó. Si la respuesta tarda 8s, a los 5s se lanza otro fetch, a los 10s otro, etc. Los requests se acumulan y pueden saturar el servidor o causar race conditions en la UI.

3. ¿Cuándo se manifiesta? Cuando el servidor es lento (alta latencia, sobrecarga) o cuando hay un pico de tráfico. El efecto bola de nieve: más requests → servidor más lento → más acumulación.

4. Corrección:

let polling = true;
let delay = 5000;
const MAX_DELAY = 60000;

async function poll() {
  while (polling) {
    try {
      const res = await fetch("/api/status");
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      const data = await res.json();
      updateUI(data);
      delay = 5000; // reset backoff en éxito
    } catch (err) {
      delay = Math.min(delay * 2, MAX_DELAY); // backoff exponencial
      console.warn("Poll error, next in", delay, "ms");
    }
    await new Promise(r => setTimeout(r, delay));
  }
}
poll();

import os, uuid, logging
from fastapi import FastAPI, HTTPException, Header
from pydantic import BaseModel, Field
import httpx, stripe, asyncpg

logger = logging.getLogger(__name__)
app = FastAPI()

stripe.api_key = os.environ["STRIPE_KEY"]  # S1, S2: de variables de entorno

HOTELES = {"H1": {"precio": 100, "nombre": "Playa Resort"},
           "H2": {"precio": 200, "nombre": "Montaña Lodge"}}

class ReservaRequest(BaseModel):  # V1: Pydantic valida tipos
    hotel_id: str
    checkin: str
    noches: int = Field(ge=1, le=30)  # V2, V3: rango válido
    token_pago: str
    email: str

@app.post("/reservar")
async def reservar(
    req: ReservaRequest,
    idempotency_key: str = Header(...),  # L1: idempotencia
):
    # V4: validar hotel
    if req.hotel_id not in HOTELES:
        raise HTTPException(404, "Hotel no encontrado")

    # V5: validar token
    if not req.token_pago.startswith("tok_"):
        raise HTTPException(400, "Token de pago inválido")

    # S3: no loggear secrets
    logger.info(f"Reserva: hotel={req.hotel_id} noches={req.noches}")

    # L3: Orden correcto — pendiente → cobrar → confirmar → notificar
    try:
        precio = HOTELES[req.hotel_id]["precio"]
        total = precio * req.noches

        # Paso 1: crear reserva pendiente
        reserva_id = await db.execute(
            "INSERT INTO reservas (hotel_id, checkin, noches, email, status, idempotency_key) "
            "VALUES ($1,$2,$3,$4,'pendiente',$5) RETURNING id",
            req.hotel_id, req.checkin, req.noches, req.email, idempotency_key
        )

        # Paso 2: cobrar
        charge = await httpx.AsyncClient().post(  # C1: async
            "https://api.stripe.com/v1/charges",
            data={
                "amount": int(total * 100),
                "currency": "usd",
                "source": req.token_pago,
                "idempotency_key": idempotency_key,
            },
            headers={"Authorization": f"Bearer {stripe.api_key}"},
            timeout=30,  # E1: timeout
        )

        # Paso 3: confirmar reserva
        await db.execute(
            "UPDATE reservas SET status='confirmada' WHERE id=$1", reserva_id
        )

        # Paso 4: notificar (asincrónico, no bloquea respuesta)
        await enviar_email_async(req.email, f"Reserva confirmada por ${total}")

        return {"status": "ok", "total": total, "reserva_id": reserva_id}

    except Exception as e:
        # E4: no exponer internals
        logger.error(f"Error en reserva: {type(e).__name__}")
        # Rollback: si se cobró pero no se confirmó, iniciar reembolso
        raise HTTPException(500, "Error procesando reserva")
